DEV LOG · 테스트 자동화

사람이 읽는 문서가 그대로 기계의 실행 스펙이 되게 만들기

테스트 케이스를 "문서 따로, 코드 따로"에서 벗어나 하나로 합친 이야기. 구조를 어떻게 잡았고, SSH 삽질부터 무결성 검사까지 어디서 넘어졌는지 기록.

✍️ Taeik 📅 2026-07-13 📦 test-automation-skeleton ⏱️ 약 6분

요약 먼저. 테스트 케이스를 사람이 읽는 YAML 시나리오로 쓰되, 그 파일을 자동화 프로젝트가 그대로 실행 스펙으로 읽게 만들었다. 화면 요소(셀렉터)·데이터(픽스처)·시나리오를 3계층으로 분리하고, 커밋 전에 validate_testcases.py로 정합성을 강제한다. 지금은 홈 화면 커버리지를 배너·상품·푸터까지 넓히는 중. 가장 크게 넘어진 곳은 코드가 아니라 SSH 인증 삽질이었다.

01왜 이걸 만들었나

테스트 케이스는 보통 두 곳에 따로 산다. 하나는 사람이 읽는 문서(스프레드시트, 위키), 하나는 자동화 코드(Playwright 스크립트). 문제는 이 둘이 항상 어긋난다는 거다. 화면이 바뀌면 코드는 고쳐도 문서는 방치되고, 문서를 고쳐도 코드에 반영이 안 된다. 결국 "테스트 문서"는 아무도 안 믿는 종이가 된다.

그래서 전제를 뒤집었다. 문서를 실행 가능한 스펙으로 만들면, 어긋날 수가 없다. 사람이 읽는 시나리오 파일 하나가 곧 자동화가 실행하는 입력이 되도록. 이게 test-automation-skeleton 저장소의 출발점이다.

"문서와 코드를 동기화하려 애쓰지 말고, 애초에 하나로 두자."

02구조 — 3계층으로 쪼갠 이유

핵심 결정은 "무엇이 바뀌면 어디만 고치면 되는가"를 기준으로 파일을 나눈 것이다. 화면 요소, 테스트 데이터, 시나리오는 바뀌는 빈도와 이유가 다르다. 그래서 계층을 분리했다.

testcases/**/*.yaml
사람이 읽는 테스트 시나리오. 동시에 자동화가 그대로 실행하는 스펙. (내 소유)
selectors/*.yaml
화면 요소 이름 → 실제 role / testId / css 매핑. (내 소유)
fixtures/*.yaml
테스트에 쓰는 실제 데이터 (계정 등). (내 소유)
automation/  — 다른 프로젝트 소유, 여기선 안 건드림
위 3계층을 읽어서 실제로 브라우저를 굴리는 Playwright 쪽.

포인트는 시나리오에 CSS나 role을 직접 쓰지 않는다는 규칙이다. 테스트 케이스는 login_button 같은 이름으로만 요소를 참조하고, 그 이름이 실제로 무엇인지는 selectors가 안다. 그래서 버튼의 클래스명이 바뀌어도 고칠 곳은 셀렉터 파일 한 줄뿐이다. 시나리오 수십 개는 그대로 산다.

테스트 케이스는 이렇게 생겼다

id: LOGIN-001
title: 로그인 성공
last_verified: 2026-07-13
steps:
  - action: navigate
    target: login_page
  - action: fill
    target: email_input
    value: "{{ fixtures.user.email }}"
  - action: click
    target: login_button
  - action: assert_visible
    target: dashboard_header

action은 정해진 어휘만 쓴다 — navigate, click, fill, select, check, uncheck, assert_visible, assert_hidden, assert_text, wait, custom. 파일 업로드나 멀티탭처럼 복잡한 동작은 action: custom + 이름표를 달아 자동화 쪽에 "이 이름으로 이런 동작 구현해달라"고 넘긴다. 구현은 그쪽 몫, 스펙 정의는 내 몫으로 경계를 그었다.

03가장 중요한 장치 — 커밋을 막는 검증기

구조를 아무리 예쁘게 잡아도, 사람이 손으로 쓰는 YAML은 반드시 깨진다. 셀렉터에 없는 요소를 참조하거나, 필수 필드를 빼먹거나, 오타 난 action을 쓴다. 그래서 validate_testcases.py가 커밋 전에 이걸 전부 잡는다.

  • 정합성 — 시나리오가 참조하는 모든 target이 selectors에 실제로 존재하는지 대조.
  • 필수 필드 — id / title / steps가 다 있는지.
  • 어휘 검사 — 정해진 action 목록 밖의 값이 있으면 오류.
  • 신선도(stale) 경고 — last_verified가 30일 넘게 지난 케이스를 따로 알려준다.
이 stale 목록이 사실상 "할 일 우선순위"다 30일 넘은 케이스 = 실제 화면을 다시 눈으로 확인해야 하는 대상. 검증기가 매번 이 목록을 뱉으니, 다음에 뭘 점검할지 고민할 필요가 없다. 오류가 하나라도 있으면 exit 1 — 깨진 채로는 커밋이 안 넘어간다.

루틴 자체를 못박아 뒀다:

  1. 실제 앱 화면을 Claude in Chrome / computer-use로 스크린샷·DOM 확인
  2. 기존 셀렉터·시나리오와 달라진 점 찾기
  3. 요소만 바뀌었으면 → selectors 해당 줄만 수정
  4. 플로우가 바뀌었으면 → 해당 케이스의 steps 수정
  5. last_verified를 오늘 날짜로 갱신
  6. python3 validate_testcases.py 통과 확인 후에만 commit & push

04시행착오 — 코드가 아니라 인증에서 넘어졌다

구조나 검증 로직은 오히려 순탄했다. 진짜 시간을 잡아먹은 건 저장소에 접속하는 것, 즉 GitHub SSH 인증이었다.

삽질 1 — 도구가 아예 없었다

샌드박스에서 SSH를 쓰려는데 openssh-client가 안 깔려 있었다. apt-get install로 해결. 사소하지만 "환경이 당연히 갖춰져 있겠지"라는 가정이 처음부터 틀렸다는 신호였다.

삽질 2 — 있는 키를 두고 새 키를 만들 뻔했다

여기가 진짜 교훈. 인증이 막히자 셋업 스크립트가 냉큼 새 SSH 키를 생성하고 "이 공개키를 GitHub에 등록하세요"로 넘어갔다. 그런데 사실 SSH 접근은 이미 설정돼 있었다. 등록된 지문은:

# 이미 GitHub에 등록돼 있던 키
SHA256:W9V18Bdai6IUIfgOdNSKTVQmUtMipN/DBtuHINJDCwQ

새 키를 만드는 건 문제를 푸는 게 아니라 새 문제를 하나 더 만드는 것이었다. 등록 페이지를 열고, 키를 붙여넣고, 확인하고… 이미 되던 걸 처음부터 다시 하는 셈.

여기서 원칙 하나를 박제했다 — "만들기 전에 확인한다" 인증이 막히면 가장 먼저 기존 키의 지문이 GitHub에 등록된 것과 일치하는지부터 대조한다. 새 키 생성은 최후의 수단. 이 원칙 덕에 다음부터는 "일단 키부터 만들자"는 반사행동을 멈추게 됐다.

삽질 3 — 프록시 위에 얹기

샌드박스가 이미 GIT_SSH_COMMAND 프록시를 깔아둔 경우가 있어서, 덮어쓰지 않고 그 위에 identity만 얹도록 셋업 스크립트를 고쳤다:

export GIT_SSH_COMMAND="${GIT_SSH_COMMAND:-ssh} -i $IDENTITY -o IdentitiesOnly=yes -o StrictHostKeyChecking=no"

기존 환경을 존중하면서 필요한 것만 추가하는 방식. 환경을 통째로 내 방식대로 갈아엎으려다 깨진 경험의 반작용이다.

05지금 고도화하는 방향

초기엔 홈 화면의 헤더 + 카테고리 섹션만 커버했다. 지금은 커버리지를 넓히는 중이다:

  • 배너 섹션 — 캐러셀·프로모션 배너의 노출/전환 확인
  • 상품 섹션 — 상품 카드 렌더링, 목록 정합성
  • 푸터 섹션 — 링크·정보 영역 검증

넓힐수록 앞서 만든 3계층 분리와 검증기가 빛을 본다. 새 섹션을 추가한다는 건 대부분 selectors에 요소 몇 개 등록하고 시나리오를 얹는 일이라, 화면이 흔들려도 유지보수 비용이 선형으로만 늘어난다.

배운 것 세 줄. ① 문서와 코드를 동기화하려 하지 말고 하나로 둬라. ② 사람이 쓰는 파일은 반드시 깨지니, 커밋을 막는 자동 검증을 먼저 깔아라. ③ 막히면 새로 만들기 전에 이미 있는 걸 확인하라 — 대부분의 삽질은 "확인"을 건너뛴 데서 나온다.

다음 글에서는 action: custom 케이스를 자동화 프로젝트와 어떻게 주고받는지, 그리고 stale 경고를 실제 점검 루틴으로 돌리는 방법을 다룰 예정이다.
