초기 설계

테스트 명세를 자동화 실행에 연결하는 방법

시나리오, 화면 식별 규칙, 테스트 데이터를 나누고 명세와 실행의 연결을 관리한 기록.

작성 Taeik게시 2026-07-13편집 2026-09-24
테스트 문서와 자동화가 같은 기준을 읽도록 만들었다.

시나리오, 화면 요소를 찾는 규칙, 테스트 데이터를 분리하면 변경의 영향을 좁힐 수 있다. 다만 파일을 공유하는 것만으로 정확성이 보장되지는 않는다. 참조 오류를 검사하고, 기대 결과가 실제 코드로 검증되는지 함께 확인해야 한다.

2026-07-13의 초기 설계 기록이다. 당시에는 YAML을 직접 작성했다. 이후 운영에서는 CSV를 편집 원본으로 사용하고 YAML을 생성하는 방식으로 바뀌었다. 이 차이는 CI 운영 구조에서 다룬다.

이 글의 순서
  1. 같은 테스트를 두 번 관리하는 문제
  2. 변경 이유에 따라 세 가지 책임을 나눴다
  3. 동작과 기대 결과를 함께 쓴다
  4. 실행 전에 잡을 오류와 실행해야 알 수 있는 오류
  5. 변경을 반영하는 순서

1. 같은 테스트를 두 번 관리하는 문제

QA(Quality Assurance, 품질 보증) 업무에서 테스트케이스는 어떤 조건에서 무엇을 하고, 어떤 결과를 확인할지 정한 명세다. 이 글에서는 테스트케이스를 TC라고 줄여 쓴다.

명세를 문서에 쓰고 자동화 코드를 따로 관리하면 변경 사항을 두 곳에 반영해야 한다. 예를 들어 로그인 후 도착 화면이 바뀌었을 때 코드만 수정하면 문서의 기대 결과가 실제 검사와 달라진다. 이 상태에서는 테스트가 통과해도 어떤 요구사항을 확인했는지 설명하기 어렵다.

초기 설계의 목표는 사람이 읽는 시나리오를 실행 엔진의 입력으로도 사용하는 것이었다. YAML은 들여쓰기로 구조를 표현하는 텍스트 형식이다. 변경 내용을 Git에서 비교하기 쉽고, 단계별 동작을 표현할 수 있어 초기 입력 형식으로 선택했다.

2. 변경 이유에 따라 세 가지 책임을 나눴다

구성담는 내용수정하는 상황
시나리오
testcases/		TC ID, 실행 순서, 기대 결과사용자 흐름이나 검증 목적이 바뀔 때
셀렉터
selectors/		버튼, 입력란 등 화면 요소를 찾는 규칙요소의 이름, 역할, 화면 구조가 바뀔 때
테스트 데이터
fixtures/		검색어, 상품 경로 등 반복 실행에 쓰는 값상품이나 실행 조건이 바뀔 때

시나리오는 login_button 같은 의미 있는 이름을 참조한다. 실제 버튼을 찾는 규칙은 셀렉터 파일이 맡는다. 이렇게 하면 버튼의 식별 규칙만 바뀐 경우 시나리오 전체를 수정할 필요가 줄어든다. 사용자 흐름까지 달라졌다면 시나리오도 다시 검토해야 한다.

여기서 fixture는 테스트에 사용할 데이터 묶음을 뜻한다. 준비와 정리 절차를 실행하는 Playwright의 fixture와는 역할이 다르다.

3. 동작과 기대 결과를 함께 쓴다

다음은 초기 YAML 구조를 설명하기 위한 예시다. 실제 실행에는 각 target에 대응하는 페이지 주소와 요소 정의가 필요하다.

id: LOGIN-001
title: 로그인 후 대시보드가 표시된다
steps:
  - action: navigate
    target: login_page
  - action: fill
    target: email_input
    value: "qa@example.com"
  - action: fill
    target: password_input
    value: "example-password"
  - action: click
    target: login_button
  - action: assert_visible
    target: dashboard_header

click은 버튼을 누르는 동작이고, assert_visible은 대상이 보이는지 검사하는 판정이다. 자동화에서는 이런 결과 검사를 assertion이라고 부른다. 버튼을 눌렀다는 사실만으로 로그인 성공을 판단해서는 안 된다.

예시의 제목 노출 검사는 출발점이다. 실제 로그인 테스트라면 목적지, 로그인 사용자 식별, 세션 상태 중 요구사항에 맞는 성공 기준을 더 정해야 한다. 로마스토어에서도 이후 화면 노출 중심 검사를 수량과 금액 검증으로 강화했다.

4. 실행 전에 잡을 오류와 실행해야 알 수 있는 오류

검사 시점확인할 내용이 검사만으로 알 수 없는 것
파일 검증ID 중복, 필수 필드, 지원 동작, 셀렉터와 데이터 참조실제 화면에서 버튼이 동작하는지
브라우저 실행요소 탐색, 사용자 동작, 요구사항에 맞는 결과실행하지 않은 조건의 정상 여부
주기적 검토최근 확인일, 정책 변경, 테스트 데이터 유효성검토일만으로 보장되는 실행 안정성

초기 기록에서는 로컬 검증기를 커밋 전에 실행하는 절차를 정했다. 그러나 7월 30일 재검토에서 해당 검증기가 저장소에 포함되지 않은 문제를 확인했다. 실행 지침이 있다는 사실과 자동으로 적용되는 통제 장치가 있다는 사실은 다르다. 이후에는 저장소 안의 검사와 CI, 즉 변경할 때 자동으로 검증하는 과정으로 옮기는 것이 핵심 과제가 됐다.

마지막 확인일이 오래된 TC는 재검토 후보로 볼 수 있다. 날짜가 오래됐다고 곧바로 실패한 TC로 분류하거나, 날짜만 갱신해 검증 완료로 처리하지 않는다.

5. 변경을 반영하는 순서

  1. 현재 화면과 요구사항을 확인하고, 달라진 것이 식별 규칙인지 사용자 흐름인지 구분한다.
  2. 시나리오, 셀렉터, 테스트 데이터 중 해당 책임을 가진 원본을 수정한다.
  3. 파일 간 참조와 생성물의 일치 여부를 검사한다.
  4. 영향받는 테스트를 실행하고 기대 결과를 확인한다.
  5. 실행 환경, 결과, 확인하지 못한 범위를 기록한 뒤 검증일을 갱신한다.

이 구조의 효과는 “문서가 절대 어긋나지 않는다”가 아니다. 변경의 출처를 줄이고, 어긋났을 때 검출할 수 있는 지점을 만드는 데 있다. QA가 관리해야 할 핵심은 파일 형식보다 검증 의도와 실제 판정의 연결이다.
