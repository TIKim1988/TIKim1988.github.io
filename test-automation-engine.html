DEV LOG · 테스트 자동화

YAML 한 줄을 브라우저 클릭으로 — 실행 엔진을 만들고 굴린 기록

사람이 읽는 시나리오는 지난 글에서 만들었다. 이번엔 그 YAML을 진짜 브라우저 동작으로 바꾸는 인터프리터를 세우고, 가짜 화면에서 굴려보고, 실제 앱에 붙이기까지. 코드보다 설치·flaky·경계 판단에서 더 넘어졌다.

✍️ Taeik 📅 2026-07-13 📦 test-automation-skeleton ⏱️ 약 7분
요약 먼저. 사람이 쓴 YAML 시나리오를 읽어 Playwright 명령으로 번역하는 인터프리터를 만들었다. 스텝 어휘는 11개로 고정하고, 그걸로 못 담는 동작(파일 업로드·다중 탭 등)은 action: custom이라는 확장점 하나로 몰아 스펙 정의 프로젝트와 경계를 그었다. 개발은 demo-app이라는 가짜 화면 위에서 하고, 실제 앱엔 baseURL만 바꿔 붙인다. 정작 시간을 잡아먹은 건 인터프리터 로직이 아니라 Playwright 브라우저 설치, flaky 테스트, 그리고 "이 로직을 어디에 둘 것인가"라는 경계 판단이었다.

01이 프로젝트가 맡은 것 — 경계부터

지난 글의 프로젝트는 스펙을 소유한다. 무엇을 테스트할지, 화면 요소를 뭐라 부를지(testcases/, selectors/, fixtures/)를 관리한다. 이 프로젝트는 그걸 실행한다. 같은 저장소 안에 살지만 소유 영역이 다르다.

가장 먼저 못 박은 규칙은 "이 프로젝트는 testcases/selectors/fixtures를 읽기만 한다"는 거였다. 실행하다 셀렉터가 틀린 걸 발견해도 내가 직접 고치지 않는다. 고칠 내용을 정리해서 스펙 쪽에 넘긴다. 경계를 흐리는 순간 "문서와 코드를 하나로 둔다"는 전제 자체가 무너지기 때문이다.

testcases / selectors / fixtures  — 읽기 전용
스펙 소유 프로젝트가 관리. 여기선 입력으로만 받는다.
automation/runner/interpreter.ts  — 내 소유
YAML 스텝 → Playwright 명령으로 번역하는 해석기.
automation/steps/custom.ts  — 내 소유
기본 어휘로 못 담는 로직의 확장점.
automation/tests/*.spec.ts  — 내 소유
인터프리터를 구동하는 Playwright 진입점.

02인터프리터 — YAML을 Playwright로 번역하기

핵심은 단순하다. 시나리오의 스텝 하나를 읽어 action을 보고, 그에 맞는 Playwright 호출로 바꾼다. 스텝의 target은 셀렉터 파일을 거쳐 실제 로케이터로 풀린다. 대략 이런 모양이다.

async function runStep(page, step, sel, fx) {
  const locator = () => page.locator(resolve(sel, step.target)); // 이름 → 실제 셀렉터
  switch (step.action) {
    case "navigate":       return page.goto(resolve(sel, step.target));
    case "click":          return locator().click();
    case "fill":           return locator().fill(interpolate(step.value, fx));
    case "assert_visible": return expect(locator()).toBeVisible();
    case "assert_text":    return expect(locator()).toHaveText(step.value);
    // select / check / uncheck / assert_hidden / wait ...
    case "custom":         return runCustom(step.name, { page, step, sel, fx });
    default: throw new Error(`알 수 없는 action: ${step.action}`);
  }
}

어휘는 딱 11개로 고정했다 — navigate, click, fill, select, check, uncheck, assert_visible, assert_hidden, assert_text, wait, custom. 어휘를 늘리고 싶은 유혹이 계속 온다. "hover도 넣을까, double_click도…" 하지만 어휘가 늘수록 스펙을 쓰는 사람이 외워야 할 게 늘고, 인터프리터의 switch도 비대해진다. 그래서 규칙을 세웠다 — 기본 어휘는 "화면을 읽고 쓰는 최소 동작"까지만. 그 밖은 전부 다음 장의 custom으로.

03못 담는 건 전부 custom.ts 하나로

파일 업로드, 다운로드 검증, 다중 탭, 드래그 앤 드롭… 이런 건 fill 한 줄로 안 된다. 여기서 두 갈래 길이 있었다.

  • A안 — 필요할 때마다 인터프리터에 case를 추가한다. 당장은 편하다.
  • B안 — 복잡한 동작은 전부 action: custom + 이름표로 받고, 구현은 custom.ts에 몰아둔다.

B안을 택했다. 이유는 경계 때문이다. 스펙을 쓰는 사람은 "이런 동작이 필요하다"는 이름만 선언하면 된다. 실제로 그 이름이 무슨 짓을 하는지는 이 프로젝트의 몫이다.

# 스펙 쪽 YAML — "무엇이 필요한지"만 선언
- action: custom
  name: upload_profile_image
  value: "fixtures/avatar.png"
// custom.ts — "실제로 어떻게" 는 여기 몫
register("upload_profile_image", async ({ page, step }) => {
  const [chooser] = await Promise.all([
    page.waitForEvent("filechooser"),
    page.getByTestId("avatar-upload").click(),
  ]);
  await chooser.setFiles(step.value);
});

덕분에 스펙은 얇게 유지되고, 지저분한 브라우저 제어 코드는 한 파일에 격리된다. "스펙 정의는 저쪽, 구현은 이쪽"이라는 선을 코드 구조로 강제한 셈이다.

복잡함을 없앨 수 없으면, 한 곳에 가둬라. 어휘를 늘리는 대신 확장점 하나를 판 이유.

04가짜 화면(demo-app) 위에서 먼저 굴린다

뼈대를 만들 땐 실제 앱이 걸림돌이다. 로그인 막히고, 데이터 바뀌고, 느리고, 남의 서버라 마음대로 못 건드린다. 그래서 demo-app/이라는 가짜 화면을 하나 뒀다. 인터프리터·셀렉터 규칙·custom 확장이 제대로 도는지 검증하는 용도다.

실제 앱으로 옮길 땐 코드를 고치는 게 아니라 설정 두 줄만 바꾼다. playwright.config.ts의 baseURL과 webServer를 실제 앱으로 돌리고 demo-app/은 지운다.

// playwright.config.ts — 개발용 → 실제 앱, 스위치는 여기 한 곳
export default defineConfig({
  use: { baseURL: process.env.BASE_URL ?? "http://localhost:4173" },
  webServer: process.env.BASE_URL
    ? undefined                                  // 실제 앱: 직접 안 띄움
    : { command: "npm run demo", port: 4173 },   // 개발: demo-app 자동 기동
});

포인트는 테스트 로직이 어느 화면을 상대하는지 몰라도 된다는 것. 시나리오도 인터프리터도 그대로, 상대 서버만 갈아끼운다.

05시행착오 — 넘어진 건 로직이 아니었다

인터프리터 switch 자체는 순탄했다. 진짜 시간을 먹은 건 그 주변이었다.

삽질 1 — Playwright 브라우저 설치가 sudo에서 막힘

샌드박스에서 npx playwright install --with-deps chromium을 돌렸더니 시스템 라이브러리 설치 단계에서 권한이 없어 실패했다. --with-deps는 apt-get으로 OS 패키지를 깔려 하는데, 그 권한이 없었던 것. 해법은 2단계 폴백이었다 — 되면 --with-deps, 안 되면 브라우저 바이너리만이라도 받는다.

# 권한 되면 전부, 막히면 브라우저 바이너리만이라도
npx playwright install --with-deps chromium || npx playwright install chromium

|| 한 줄이지만 교훈은 명확했다 — "환경이 당연히 갖춰져 있겠지"라는 가정부터 틀린다. (지난 글의 openssh-client가 아예 없던 것과 같은 종류의 실수다. 인증 삽질은 그 글에서 이미 다뤘으니 여기선 한 줄로 넘어간다.)

삽질 2 — flaky, 진짜 실패인 척하는 가짜 실패

실제 앱에 붙이자 같은 테스트가 됐다 안 됐다 하기 시작했다. 원인은 대개 타이밍이다 — 요소가 뜨기 전에 클릭하거나, 애니메이션 중에 텍스트를 읽거나, 네트워크가 느린 순간에 걸린다. 여기서 반사적으로 wait: 3000 같은 고정 대기를 흩뿌리고 싶은 유혹이 온다. 그건 테스트를 느리게 만들면서 근본은 못 고친다.

대신 두 가지로 잡았다. 첫째, 인터프리터의 assert를 전부 Playwright의 자동 대기(web-first assertion)에 태웠다. toBeVisible()은 요소가 나타날 때까지 알아서 기다린다. 둘째, 그래도 남는 진짜 flaky는 숨기지 않고 재시도 횟수를 명시해 드러냈다.

// flaky를 0으로 숨기지 말고, 몇 번 흔들리는지 보이게
retries: process.env.CI ? 2 : 0,
reporter: [["html"], ["list"]],   // 실패 리포트로 원인 추적
고정 sleep은 flaky의 진통제일 뿐 wait 스텝은 어휘에 넣어두긴 했지만 최후의 수단으로만 쓴다. "요소가 뜰 때까지"를 조건으로 기다리는 게 원칙이고, "몇 초"를 기다리는 건 예외다. 이 규칙을 안 세우면 시나리오가 온통 wait로 도배되면서 느려지고, 정작 진짜 버그는 대기 뒤에 숨는다.

삽질 3 — "이 로직 어디 두지?"가 제일 오래 걸렸다

기술적 버그보다 판단이 더 오래 걸렸다. 새 동작이 필요할 때마다 매번 같은 질문 앞에 섰다 — 인터프리터에 기본 case로 넣나, custom.ts로 빼나? 결국 기준을 문장으로 고정하고 나서야 고민이 멈췄다.

  • 여러 시나리오가 공통으로 쓰는 화면 동작이고 어휘로 자연스럽게 이름 붙는다 → 인터프리터 기본 case.
  • 특정 기능에만 쓰이거나 브라우저 제어가 지저분하다(업로드·다중 탭 등) → custom.ts.

기준이 없을 땐 그때그때 기분으로 갈렸고, 그 결과 비슷한 로직이 두 곳에 흩어졌다. 기준 한 줄이 리팩터링 몇 시간을 아꼈다.

06구축에서 운영으로 넘어가며 세운 루틴

이제 뼈대는 섰고, 초점은 "안 깨지게 굴리기"로 옮겨갔다. 반복 작업은 순서로 못 박아 뒀다.

  1. 스펙 쪽에서 새 시나리오/셀렉터가 넘어오면 git pull로 읽기 전용 입력을 갱신.
  2. demo-app에서 먼저 돌려 인터프리터가 새 스텝을 이해하는지 확인.
  3. 기본 어휘로 안 되면 → custom.ts에 이름표 붙여 구현.
  4. 실제 앱(BASE_URL)으로 돌려 flaky 여부 확인 — 흔들리면 원인(타이밍/셀렉터)부터 추적.
  5. CI에서 retries·리포트로 안정성 지표를 남기고, 실패는 숨기지 말고 드러낸다.
배운 것 세 줄. ① 실행 엔진의 어휘는 최소로 고정하고, 복잡함은 custom 확장점 하나에 가둬라. ② 뼈대는 실제 앱이 아니라 가짜 화면(demo-app) 위에서 세우고, 전환은 설정 한 곳으로. ③ 넘어지는 건 대개 로직이 아니라 환경 설치·flaky·경계 판단이다 — 각각을 폴백 한 줄, 자동 대기, 기준 문장으로 막아둬라.

다음 글에서는 custom.ts에 쌓인 확장들을 어떻게 정리하는지, 그리고 CI 실패 리포트를 스펙 쪽 last_verified 갱신 루틴과 어떻게 연결하는지를 다룰 예정이다.
