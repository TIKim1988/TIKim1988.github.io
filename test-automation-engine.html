YAML 시나리오를 실행하는 Playwright 엔진 설계

실행 규칙과 업무별 검증의 책임을 나누고, 실패한 계층에 맞춰 원인을 분석하는 방법.

작성 Taeik게시 2026-07-13편집 2026-09-24
실행 엔진의 역할은 시나리오를 브라우저 동작과 결과 검사로 정확하게 연결하는 것이다.

공통 동작은 작은 실행 규칙으로 유지하고, 상품 수량이나 장바구니 금액처럼 업무에 특화된 검증은 별도 함수로 분리했다. 이렇게 나누면 화면이 바뀌었을 때 명세와 실행 코드 중 어디를 수정해야 하는지 판단하기 쉽다.

2026-07-13에 시작한 엔진 설계 기록이다. 초기의 예제 화면 검증과 이후 로마스토어 적용을 구분해 설명한다. 현재 운영 명령과 실행 범위는 CI 운영 구조를 기준으로 확인할 수 있다.

이 글의 순서
  1. 시나리오 한 줄이 실행되는 과정
  2. 기본 동작은 작게, 복합 검증은 명시적으로
  3. 엔진 검사와 서비스 검사를 분리한다
  4. 기다릴 시간보다 기다릴 상태를 정한다
  5. 실패한 계층에 맞춰 수정한다

1. 시나리오 한 줄이 실행되는 과정

Playwright는 브라우저에서 클릭, 입력, 화면 검사를 수행하는 테스트 도구다. YAML은 들여쓰기로 데이터 구조를 표현하는 텍스트 형식이다. 이 프로젝트는 YAML 시나리오를 읽는 해석기(interpreter)를 Playwright 위에 두었다. 해석기는 각 단계의 동작 이름을 확인하고 해당 Playwright 명령을 호출한다.

시나리오 읽기 → 동작과 대상 확인 → 화면 요소 찾기 → 동작 수행 → 기대 결과 검사
구성책임예시
시나리오실행 순서와 검사할 대상 정의검색어 입력 후 결과 확인
셀렉터와 데이터요소를 찾는 규칙과 입력값 제공검색창의 역할, 지정 검색어
해석기지원하는 동작을 Playwright 호출로 변환fill, click, assert_text
업무별 검증 함수여러 화면이나 값의 관계 확인수량 변경에 따른 금액 계산

로케이터(locator)는 실행 시점에 화면 요소를 찾고 조작하기 위한 Playwright 객체다. 셀렉터 파일의 정의를 읽어 로케이터를 만든다. 버튼의 역할과 이름처럼 사용자가 인식하는 속성으로 찾고, 같은 이름이 반복되면 검색 범위를 특정 영역으로 좁힌다. Playwright 로케이터 문서에서 이 방식의 동작을 확인할 수 있다.

2. 기본 동작은 작게, 복합 검증은 명시적으로

초기 엔진의 기본 동작은 이동, 클릭, 입력, 선택, 체크, 체크 해제, 노출 검사, 숨김 검사, 텍스트 검사, 대기, 사용자 정의 동작의 11개였다. 동작을 추가할 때마다 시나리오 형식, 검증기, 해석기를 함께 수정해야 하므로 업무별 요구를 무조건 기본 동작으로 늘리지 않았다.

예를 들어 “장바구니 수량을 늘리고 금액을 확인한다”는 클릭 한 번의 문제가 아니다. 변경 전 기준 금액, 변경 후 수량, 상품 금액과 합계의 관계를 함께 읽어야 한다. 이런 검증은 custom, 즉 이름을 붙인 별도 함수로 연결한다.

# 구조를 설명하기 위한 예시이며 실제 등록 이름과는 다를 수 있다.
- action: custom
  name: verify_cart_quantity_and_amount

사용자 정의 함수는 복잡한 동작을 담을 수 있지만, 이름만 보고 무엇을 검사하는지 알 수 있어야 한다. 함수 안에서 입력만 하고 결과를 확인하지 않거나, 여러 실패를 한꺼번에 무시하면 명세의 의미가 약해진다. 실행 보고서에는 준비, 동작, 판정을 구분해 남기는 것이 좋다.

3. 엔진 검사와 서비스 검사를 분리한다

초기 엔진은 예제 화면인 demo-app에서 먼저 검증했다. 외부 사이트의 로그인 정책이나 상품 변화에 영향을 받지 않고, 입력한 시나리오가 의도한 브라우저 명령으로 연결되는지 확인하기 위해서다.

예제 화면 통과는 실서비스 통과를 뜻하지 않는다. 실제 서비스로 연결할 때는 주소 설정 외에도 셀렉터, 인증 조건, 테스트 데이터, 기대 결과를 확인해야 한다. 초기 글에서 “설정 두 줄만 바꾸면 된다”고 설명했던 부분은 이 차이를 충분히 담지 못했다.

검증 대상대표 질문
실행 엔진정의된 동작을 처리하는가? 누락된 데이터나 알 수 없는 동작을 명확히 실패시키는가?
실제 서비스상품이 올바르게 담기는가? 수량, 금액, 선택 상태가 요구사항과 일치하는가?
실행 환경브라우저가 시작되는가? 필요한 시스템 구성과 네트워크 접근이 가능한가?

4. 기다릴 시간보다 기다릴 상태를 정한다

“3초 뒤 검사”보다 “담기 완료 안내가 나타난 뒤 장바구니를 검사”하는 편이 목적을 분명하게 드러낸다. Playwright의 자동 대기 검증은 제한 시간 안에서 조건이 만족되는지 반복 확인한다. 그래도 조건이 충족되지 않으면 실패로 남겨야 한다.

간헐적으로 성공과 실패가 바뀌는 현상을 flaky라고 부른다. 렌더링 시점뿐 아니라 상품 데이터, 네트워크, 상태 공유, 실제 서비스 결함도 원인이 될 수 있다. 이를 “가짜 실패”라고 단정하면 조사할 신호를 놓친다.

테스트 전체 재시도와 한 검사의 자동 대기는 다르다. 재시도에서 통과한 결과는 첫 실행 통과와 구분한다. Playwright의 재시도 분류도 처음 실패한 뒤 재시도에서 성공한 테스트를 flaky로 구분한다.

5. 실패한 계층에 맞춰 수정한다

  • 브라우저가 시작되지 않음: 환경 문제로 분류한다. 이 결과만으로 서비스 결함을 보고하지 않는다.
  • 요소를 찾지 못함: 셀렉터뿐 아니라 진입 화면, 팝업, 접근 정책, 데이터 조건을 확인한다.
  • 동작은 끝났지만 결과가 다름: 기대 결과와 서비스 정책을 대조한다. 통과시키기 위해 검사를 노출 확인으로 바꾸지 않는다.
  • 일부 실행에서만 실패함: 실패 시점과 상태를 보존하고 재현 조건을 좁힌다. 재시도 성공만으로 종결하지 않는다.

엔진을 단순하게 유지하는 이유는 코드량 자체를 줄이기 위해서만은 아니다. 실패가 명세, 화면 식별, 데이터, 서비스 동작 중 어느 지점에서 발생했는지 설명할 수 있어야 수정도 검증도 정확해진다.
