로마스토어 E2E 재설계: 노출 확인에서 결과 검증으로

23개 테스트를 검토하고 수량, 금액, 정렬 결과 중심으로 성공 판정을 강화한 기록.

작성 Taeik게시 2026-09-08편집 2026-09-24
23개 테스트를 검토한 결과, 우선 과제는 테스트 수를 늘리는 것이 아니라 성공 판정을 강화하는 일이었다.

49개 결과 검사 중 48개가 화면 요소의 노출만 확인했다. 수량과 금액, 실제 정렬 순서까지 검증하도록 수정한 뒤 전체 23개 중 21개가 통과했고, 가격 정렬 2개는 실패로 남았다.

초기 분석은 2026-09-07, 수정 후 검증은 2026-09-08 기준이다. 이후 29개로 확장된 명세는 별도 글에 기록했다. 아래의 11개 “검증 묶음”은 설계 분류이며 실행 테스트 수가 아니다. 이 글의 검토 문서 내려받기

1. 무엇을 확인했는가

E2E(End-to-End) 테스트는 사용자가 거치는 여러 화면과 기능을 연결해 검사하는 방식이다. 이 프로젝트의 범위는 로마스토어의 비회원 탐색, 상품 상세, 장바구니, 주문서 진입이다. 최종 결제와 주문 생성은 포함하지 않는다.

TC는 사전조건, 동작, 기대 결과를 묶은 테스트케이스다. 이 저장소에서는 표 데이터를 텍스트로 저장한 CSV를 명세 원본으로 사용하고, 실행용 구조 파일인 YAML을 생성한다.

초기 실행의 8개 실패는 서비스 결함 8건이 아니다. 브라우저가 시작되지 않은 환경 오류다. 검색 결과 화면을 직접 조회한 사실도 검색어 입력부터 제출까지의 흐름이 통과했다는 증거로 사용하지 않았다.

2. 발견 사항을 결과 신뢰도에 따라 정리했다

발견 사항은 자동화 실행과 판정의 신뢰도를 기준으로 정리했다. 이 분류는 서비스 결함의 심각도와는 구분한다. 셀렉터는 요소를 찾는 규칙이며, 로케이터는 그 규칙에 따라 브라우저에서 대상을 찾고 조작하는 객체다.

F01. 결과 보고가 실행되지 않았다

결과 요약 스크립트의 문자열 안에 잘못 들어간 백틱 때문에 문법 오류가 발생했다. node --check scripts/summarize-results.mjs로 재현했다. TypeScript 검사만으로는 이 JavaScript 파일의 오류를 잡지 못했다. 보고서 문법 검사를 별도로 추가하고, 요약 실패도 CI 실패에 반영하도록 수정했다.

F02. “보인다”가 “올바르다”를 대신했다

수량 버튼을 누른 뒤 주문 버튼만 확인하면 수량이 바뀌지 않아도 통과할 수 있다. 결제수단이 보여도 실제 선택됐는지는 알 수 없다. 정렬 버튼이 보여도 상품 순서가 틀릴 수 있다. 검사의 중심을 동작 후 값과 상태로 옮겼다.

기능기존 판정의 한계강화한 판정
수량 변경관련 버튼 노출수량 1 → 2 → 1, 기준 금액 × 수량
카테고리와 결제수단클릭한 요소 노출선택 상태, 이전 선택 해제, 대응 영역
상품 정렬제목이나 정렬 링크 노출표시 판매가의 실제 오름차순과 내림차순
장바구니와 주문서화면 진입과 버튼 노출상품 식별값, 수량, 화면 사이 상품 금액 일치

F03. 다른 화면의 요소 정의가 서로 덮어써졌다

셀렉터 파일을 Object.assign으로 합치는 과정에서 같은 이름의 정의가 덮어써졌다. 중복 이름은 8종이었고, 검색과 스토어의 정렬 요소는 역할과 이름도 달랐다. 실제 로더 호출에서 검색 정렬 정의가 스토어 정의로 바뀌는 것을 확인했다. 화면별 이름을 분리하고 중복을 오류로 처리했다.

F04. 검색 화면의 실제 역할과 정의가 달랐다

검색 입력란은 searchbox였지만 정의는 textbox였고, 검색 정렬은 버튼인데 링크로 찾고 있었다. 현재 화면의 역할에 맞게 수정했다. 요소 정의 수정만으로 완료 처리하지 않고 입력, 검색어 반영, 결과 목록을 다시 검증했다.

F05. 주문자와 수령자의 입력 범위를 구분하지 않았다

이름과 전화번호를 화면 전체에서 같은 규칙으로 찾고 있었다. 여러 입력란이 함께 있으면 대상을 하나로 정하지 못하거나 잘못된 입력란을 선택할 위험이 있다. 입력 대상을 분리하고, 주문자와 수령자에 서로 다른 값을 넣어 각각 유지되는지 확인했다.

F06. 실행 상태가 명세와 코드에서 달랐다

명세는 active였지만 상품 TC 2개는 코드에서 별도로 건너뛰었다. 격리 상태(quarantine)도 일반 실행에서 제외되지 않았다. 상태를 한 곳에서 관리하도록 정리하고, 격리 대상은 별도로 재검증할 수 있게 했다. 기존 테스트용 ID가 없다는 이유만으로 검증을 포기하지 않고 현재 상품명과 수량 표시를 이용했다.

F07. 장바구니 준비는 있었지만 성공 확인이 없었다

11개 TC에 상품 담기 준비 단계가 있었다. 문제는 담기 클릭 직후 완료를 확인하지 않고 장바구니로 이동한다는 점이었다. 과거의 빈 장바구니 화면만으로 요청 중단이나 초기화 경쟁을 원인으로 확정할 수는 없다. 담기 완료 안내, 상품 행, 수량을 차례로 확인하도록 수정했다.

F08. 입력 오류와 실행 오류가 보고에서 빠질 수 있었다

없는 데이터 변수를 참조해도 빈 문자열로 바뀌는 동작을 재현했다. 생성 경로 중복과 사용자 정의 함수 등록 검사를 보강하고, 결과에는 통과, 실패, 재시도 통과(flaky), 건너뜀(skipped), 실행 오류를 분리했다. 테스트가 수집되지 않거나 핵심 대상이 빠진 결과도 성공으로 해석하지 않도록 판정을 강화했다.

3. 수정 후 무엇이 달라졌는가

가격낮은순은 통과했지만 높은가격순에서 표시 판매가의 역전이 남았다. 검색에서는 83,000원 다음 106,600원, 스토어에서는 377,000원 다음 399,000원이 표시됐다. 이 값은 당시 재현 데이터이며 현재 가격을 뜻하지 않는다.

확인한 사실: 표시 판매가 기준의 내림차순과 화면 순서가 일치하지 않았다. 미확인 사항: 서비스가 정가 등 다른 값을 정렬 기준으로 사용하는지 여부다. 정책을 확인하지 않은 채 테스트를 약화하거나 성공으로 바꾸지 않았다. 서비스 코드와 데이터 준비 API는 이 저장소에 없어 서비스 동작 수정까지 완료하지 못했다.

구현에서는 기존 CSV/YAML 실행 구조를 유지하고, 공통 장바구니와 주문서 동작을 CommercePage로 분리했다. 아래에서 제안한 독립 TypeScript 테스트와 전용 준비 구조로 전부 이관한 것은 아니다.

5. 명세, 화면 동작, 테스트 준비의 책임을 나눈다

후속 구조에서는 CSV가 위험과 기대 결과를 관리하고, TypeScript 테스트 코드가 실제 판정을 표현하도록 제안했다. Page Object는 화면별 요소와 동작을 묶는 객체이며, fixture는 테스트 시작 상태를 준비하고 정리하는 장치다.

  • 명세: ID, 검증 목적, 사전조건, 기대 결과, 실행 코드 연결을 관리한다.
  • 화면 객체: 요소의 탐색 범위와 클릭, 입력 같은 동작을 관리한다.
  • 준비 절차: 각 테스트에 독립된 비회원 상태와 상품을 준비한다.
  • 결과 검사: 상품 식별, 수량, 금액, 정렬의 기대값을 읽을 수 있게 남긴다.

장바구니를 수정하는 테스트는 준비 함수를 재사용할 수 있다. 반면 장바구니 담기 자체를 검사하는 테스트는 담기 완료를 본문의 판정에 포함해야 한다. 준비 성공과 검증 성공을 구분해야 실패 위치도 명확해진다.

6. 운영 사이트와 통제된 테스트 환경의 역할

운영 사이트에서는 승인된 세션과 상품으로 핵심 탐색 및 구매 준비 경로를 확인하고 최종 결제 전에 종료한다. 품절, 최대 수량, 할인, 배송비, 결제 실패처럼 데이터를 제어해야 하는 조건은 별도 테스트 환경에서 검증할 대상으로 분리한다.

결제대행사(PG)의 시험 환경인 sandbox와 고정 상품 데이터는 당시 확보된 전제가 아니었다. 이런 기반을 이미 사용할 수 있다고 가정해 구현 완료 범위를 넓히지 않았다. 화면 간 상품 금액이 같다는 검사도 서버의 모든 가격 계산 정책이 올바르다는 증거는 아니다.

7. 완료 기준은 실행 결과와 남은 위험으로 정한다

초기 완료 순서는 실행과 보고의 오류 복구, 대표 비회원 흐름 확인, 기존 ID별 결과 검사 보강, 회귀 범위 확대였다. 핵심 경로를 새 세션에서 10회 연속 재시도 없이 통과시키는 안정화 기준도 제안했지만, 이를 달성한 실적으로 기록하지 않았다.

9월 8일 기준 후속 범위에는 가격 정렬 정책 확인, 검색 복구, 경계값, 주문서 필수값 오류, 약관 내용, 할인과 배송비, 결제와 주문 정합성이 남았다. 한 번의 성공 결과와 장기간의 안정성은 구분해 평가한다.

8. 검토 근거를 다시 확인하는 방법

초기 분석에서 사용한 주요 정적 검사다. 9월 7일에는 마지막 문법 검사가 실패했고, 수정 후 다시 통과를 확인했다.

npm run testcases:check
npx tsc --noEmit
npx playwright test --list --reporter=list
node --check scripts/sync-testcases.mjs
node --check scripts/summarize-results.mjs

실행 기록은 날짜, 코드 버전, 대상 범위와 함께 읽어야 한다. 과거 보고서를 새로운 성공 결과로 재사용하지 않는다. 이후 명세와 검증 결과는 9월 21일 기준 29개 TC 기록에서 이어진다.
