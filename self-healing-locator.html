셀렉터 변경에 대비하는 감지와 기록 구조

자동 대체에 앞서 요소 탐색, 기록, 특성 수집을 구현한 과정과 남아 있는 검증 과제.

작성 Taeik게시 2026-07-27편집 2026-09-24
자동으로 요소를 대체하기 전에, 원래 규칙이 무엇을 찾았는지 기록할 기반부터 만들었다.

구현 범위는 요소 탐색 경로 통합, 기록 모듈, 요소 특성 수집이다. 다른 요소를 자동으로 선택해 실패를 복구하는 기능은 아직 구현 범위에 포함되지 않는다.

2026-07-27의 설계와 구현 기록이다. 2026-09-24 코드 재확인에서도 resolver는 원래 로케이터를 반환하며 healed: false를 유지한다. 아래의 후보 탐색과 자동 대체는 후속 설계다.

이 글의 순서
  1. 셀렉터를 바꿔서 통과하면 충분한가
  2. 구현한 기반과 후속 설계를 나눴다
  3. 탐색 경로를 통합하되 기존 규칙을 유지한다
  4. 요소의 특성은 선택적으로 수집한다
  5. 확인한 것과 확인하지 못한 것
  6. 자동 대체를 도입하기 위한 조건

1. 셀렉터를 바꿔서 통과하면 충분한가

셀렉터는 버튼이나 입력란을 찾는 규칙이다. 화면 구조가 달라져 기존 규칙으로 요소를 찾지 못할 때, 다른 규칙을 찾아 실행을 이어가는 접근을 self-healing, 즉 자동 복구라고 부른다.

하지만 비슷한 버튼을 찾았다고 같은 기능을 찾았다는 뜻은 아니다. “확인” 버튼이 여러 곳에 있는 화면에서 잘못된 대상을 선택하면 테스트가 통과하면서도 의도한 기능을 검사하지 않을 수 있다. 복구 성공률보다 오탐을 방지하고 판단 근거를 남기는 일이 먼저다.

또한 요소 탐색 실패는 셀렉터 변경 외에도 팝업, 접근 제한, 데이터 부재로 발생한다. 실패 원인을 확인하지 않고 모두 자동 대체 대상으로 처리하지 않는다.

2. 구현한 기반과 후속 설계를 나눴다

단계내용상태
1. 탐색 경로 통합해석기의 요소 접근을 resolveLocator에 연결구현
2. 기록 모듈복구 이벤트의 집계, 병합, 중복 제거구현. 실제 자동 복구는 꺼져 있음
3. 감지와 특성 수집원래 요소 탐색 여부와 속성을 수집선택적으로 실행하는 코드 구현
4. 대체 후보 탐색기존 특성을 기준으로 다른 식별 규칙 탐색후속 설계
5. 사용 제한과 판정신뢰도, 복구 횟수 제한, 엄격한 실패 정책후속 설계

3. 탐색 경로를 통합하되 기존 규칙을 유지한다

초안은 셀렉터가 CSS 문자열이라고 가정했지만 실제 입력은 역할, 테스트용 ID, 텍스트, CSS, 순번 등을 가진 구조였다. 초안을 그대로 적용하면 기존 입력을 해석하지 못하므로, 먼저 실제 형식에 맞춰 로케이터 생성 코드를 연결했다.

resolveLocator는 현재 원래 규칙(primary)으로 만든 로케이터를 돌려준다. 자동 대체 여부를 나타내는 healed는 false다. 함수가 하나로 모였다는 이유만으로 모든 UI 동작이 검증된 것은 아니다.

// 현재 반환 구조: 대체 후보를 선택하지 않는다.
return {
  locator,
  used: 'primary',
  healed: false,
  confidence: 1,
};

위 confidence: 1은 원래 경로를 반환할 때 쓰는 값이다. 학습된 모델이나 후보 비교를 통해 정확도 100%를 측정했다는 뜻이 아니다.

4. 요소의 특성은 선택적으로 수집한다

fingerprint는 화면 요소의 태그, 역할, 이름, 테스트용 ID, 안내 문구, 텍스트 등을 모은 기록이다. 나중에 대체 후보를 비교할 기준 자료(baseline)로 사용할 수 있다.

수집은 HEAL_CAPTURE=1을 설정했을 때만 수행한다. 없어야 정상인 요소를 확인하는 assert_hidden 같은 동작은 수집 대상에서 제외한다. 수집 모드에서도 실제 동작에 쓰는 대상은 원래 로케이터다.

다만 특성 수집에는 추가 탐색 시간이 들어간다. “대체 대상을 쓰지 않는다”와 “실행 타이밍이 완전히 같다”는 다른 주장이다. 수집 모드가 간헐적 실패에 미치는 영향은 별도로 확인해야 한다. 수집된 정보 역시 해당 테스트 전체가 통과했다는 증거와 함께 검토해야 신뢰할 수 있다.

5. 확인한 것과 확인하지 못한 것

초기 검증확인한 범위한계
타입 검사와 29개 테스트 수집코드 연결과 테스트 목록 로딩29개 브라우저 테스트의 통과를 뜻하지 않음
기록 모듈 단위 테스트가상 이벤트의 집계, 병합, 중복 제거실제 요소의 올바른 대체 여부는 검사하지 않음
브라우저 기반 수집실사이트 연결과 실행 환경에 제약이 있었음당시 실제 화면에서 수집 동작 검증을 완료하지 못함

복구 기록 파일의 totalHeals: 0은 현 단계에서는 자동 복구가 동작하지 않기 때문에 나올 수 있다. 이를 셀렉터 오류가 없다는 지표로 해석하지 않는다.

6. 자동 대체를 도입하기 위한 조건

  • 대체 후보가 하나로 특정되고, 원래 요소의 역할과 업무 목적이 일치해야 한다.
  • 어떤 규칙을 어떤 근거로 대체했는지 보고서에서 확인할 수 있어야 한다.
  • 후보가 불명확하면 실패를 유지하고, 테스트당 복구 횟수를 제한해야 한다.
  • 대체 후에도 상품, 금액, 선택 상태 등 원래 기대 결과를 검증해야 한다.
  • 자동 대체를 허용하는 관찰 실행과, 이를 실패로 다루는 엄격한 검증을 구분해야 한다.

이 조건은 구현 완료 목록이 아니라 후속 단계의 판단 기준이다. 지금까지의 성과는 자동으로 테스트를 통과시키는 기능이 아니라, 그러한 기능을 검증 가능하게 만들기 위한 탐색과 기록 기반이다.

다른 복구 방식: 이벤트 팝업은 원래 요소를 바꾸지 않고 방해 조건을 해소한다
