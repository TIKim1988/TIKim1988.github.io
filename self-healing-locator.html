DEV LOG · 테스트 자동화

셀렉터가 낡아도 안 깨지게 — 셀프힐링 로케이터 토대 만들기

화면이 조금 바뀌면 테스트가 우수수 빨개진다. 진짜 버그가 아니라 셀렉터가 낡아서. 그래서 "일단 통과는 시키되, 낡았다는 사실은 놓치지 않는" 셀프힐링을 붙이기 시작했다. 오늘은 그 토대 세 단계(STEP 1~3).

✍️ Taeik 📅 2026-07-27 📦 test-automation-skeleton ⏱️ 약 7분
요약 먼저. primary(원래 셀렉터)로 요소를 못 잡을 때, 초록 실행에서 떠둔 지문(fingerprint)으로 대신 잡아 테스트를 살리되 무엇이 낡았는지는 리포트로 남기는 게 셀프힐링이다. 오늘은 실제 힐링을 켜기 전 토대만 깔았다 — STEP 1 모든 로케이터 접근을 함수 하나로 모으고, STEP 2 힐링 기록용 heal-report.json 배관을 깔고, STEP 3 primary 감지 + 지문 캡처를 넣었다. 세 단계 모두 기본 실행 동작은 1도 안 바뀌게 설계했다. 정작 시간을 먹은 건 코드가 아니라, 채팅으로만 하다 만 작업을 진짜 GitHub 저장소에 붙이는 인증 삽질이었다.
왜 이 글이 여기서 시작하냐면 지난 작업까지는 채팅으로만 진행해서 실제 저장소에 손을 못 댔다. 이번엔 작업 환경을 저장소에 직접 붙여서, 초안으로 받아둔 셀프힐링 코드를 실제 test-automation-skeleton 위에서 이어붙였다. 그 과정에서 SSH 인증부터 다시 뚫어야 했다(뒤 05장).

01왜 셀프힐링인가 — 통과시키되, 숨기진 말자

자동화 테스트가 빨개지는 이유는 크게 둘이다. 진짜 버그거나, 셀렉터가 낡아서. 후자는 기능은 멀쩡한데 버튼 마크업이 살짝 바뀌어 getByRole 하나가 어긋난 경우다. 이게 쌓이면 "또 셀렉터 깨졌겠지" 하고 빨간불을 무시하게 되고, 그 순간 자동화는 죽는다.

셀프힐링의 발상은 단순하다. primary 셀렉터가 요소를 못 잡으면, 정상일 때 떠둔 그 요소의 생김새(지문)로 후보를 만들어 대신 잡는다. 테스트는 통과하되, "이건 힐링으로 겨우 살린 거다"라는 기록을 남긴다. 핵심 원칙 한 줄 — 통과는 시키되, 낡았다는 사실은 절대 숨기지 않는다.

그래서 전체를 다섯 단계로 쪼갰다. 각 단계는 그 자체로 안전해야 한다. 즉 힐링을 실제로 켜기 전까지는 기존 테스트 결과가 한 톨도 바뀌면 안 된다. 오늘 한 STEP 1~3은 전부 "동작 불변"이 합격 기준이었다.

STEP 1 · 배선
모든 로케이터 접근을 resolveLocator 함수 하나로 모은다. (오늘)
STEP 2 · 기록
힐링 발동을 heal-report.json 으로 남기는 recorder. (오늘)
STEP 3 · 감지 + 지문
primary 가 잡는지 짧게 감지하고, 초록일 때 지문을 떠 baseline 에 적립. (오늘)
STEP 4 · 폴백 캐스케이드
못 잡으면 지문으로 testid → role → label → text 후보를 훑는다. (다음)
STEP 5 · 신뢰도 + 가드레일
임계값, 테스트당 최대 힐링 수, 배포 게이트에선 힐링=실패(strict). (다음)

02STEP 1 — 로케이터 접근을 한 곳으로 모으기

힐링을 나중에 한 군데만 고쳐서 전체에 적용하려면, 요소를 잡는 모든 지점이 함수 하나를 통과해야 한다. 그래서 인터프리터 곳곳에 흩어져 있던 page.locator(...) 생성을 resolveLocator() 단일 진입점으로 모았다.

여기서 첫 삽질. 초안 코드는 셀렉터가 CSS 문자열이라고 가정했는데, 실제 저장소의 셀렉터는 role / testId / text / css / index를 담은 구조체(ElementDef)였다. 초안에 딸려온 배선 문서에도 "실제 코드 못 봤으니 네 스키마에 맞춰라"라고 적혀 있었다. 그래서 primary 로케이터를 만드는 기존 로직을 그대로 buildPrimaryLocator()로 옮겨 단일 생성 지점으로 삼았다.

// 모든 요소 액션이 이 한 줄을 지난다. 지금은 primary 만 돌려준다.
const { locator } = await resolveLocator(page, step.target, def, ctx);
await locator.click();   // click / fill / assert_* 전부 동일 패턴

Playwright 로케이터는 지연 평가라, 여기서 만들어 돌려줘도 실제 DOM 탐색은 뒤의 .click() 시점에 일어난다. 덕분에 함수로 한 겹 감쌌어도 타이밍까지 기존과 똑같다. 무해한 리팩터링이라는 걸 tsc 0 에러 + 테스트 29개 수집 그대로로 확인했다.

03STEP 2 — 낡음을 기록하는 heal-report

힐링은 "몰래 살려주는" 기능이라 위험하다. 기록이 없으면 셀렉터는 영영 낡은 채 방치된다. 그래서 힐링이 발동할 때마다 무엇을, 언제, 어떤 전략으로 살렸는지 이벤트로 모아 test-results/heal-report.json에 집계하는 recorder를 먼저 깔았다.

  • 전략별(testid/role/label/text)·테스트별 힐링 횟수 집계
  • 워커 여러 개나 CI 재시도 대비 기존 파일 병합 + 중복 제거
  • 테스트당 컨텍스트에 onHeal 콜백을 꽂아두고, 실행 끝에 flush

지금은 힐링이 아직 안 켜져서 리포트가 totalHeals: 0인 빈 상태로 나온다. 그래도 상관없다. 이 단계의 목적은 배관이니까. STEP 4에서 resolver가 onHeal을 부르기 시작하면 코드 한 줄 안 고치고 리포트가 채워진다. recorder 로직만은 가짜 이벤트를 넣어 집계·병합·중복제거를 유닛 테스트로 미리 검증해뒀다.

04STEP 3 — primary 감지 + 지문 캡처

힐링의 재료는 "정상일 때 그 요소가 어떻게 생겼나"다. 그걸 STEP 3에서 만든다. 두 조각이다.

  • 감지 — primary가 짧은 타임아웃 안에 요소를 잡는지 본다(isResolvable). 힐링을 발동할지 말지의 씨앗.
  • 지문 캡처 — 초록 실행에서 실제 element를 조회해 tag / testid / role / name / placeholder / text를 떠 baseline.json에 쌓는다. 셀렉터 파일은 primary만 저장하니, 폴백의 유일한 공급원이 이 지문이다.
// 캡처 모드이고 "요소가 있어야 정상"인 액션일 때만 감지 + 지문 적립.
// 액션에 실제 쓰이는 로케이터는 여전히 primary → 통과/실패 결과 불변.
if (ctx.captureEnabled && expectsPresence(ctx.action)) {
  if (await isResolvable(locator)) {
    const fp = await captureFingerprint(locator);
    if (fp) ctx.onCapture?.(logicalName, fp);
  }
}

안전장치를 두 개 박았다. 첫째, 캡처는 HEAL_CAPTURE=1일 때만 켜진다. 기본 실행은 감지 프로브조차 안 돌아서 STEP 2와 완전히 동일하다. 매 실행마다 짧은 타임아웃을 스텝 수만큼 물리는 낭비를 피하려는 거다. 둘째, assert_hidden처럼 부재가 정상인 액션은 애초에 감지/캡처에서 제외했다. 없어야 정상인 요소를 "못 잡았으니 힐링하자"로 오해하면 안 되니까.

baseline은 파일로 커밋해 둔다. CI는 매 실행이 새 체크아웃이라 메모리가 없어서, 초록 실행에서 뜬 지문을 파일에 남겨야 다음(빨강일 수 있는) 실행에서 STEP 4가 꺼내 쓴다.

05정작 넘어진 곳 — 코드 밖

지난 엔진 글에서도 그랬듯, 이번에도 로직보다 환경에서 더 넘어졌다.

  1. SSH 인증부터 다시. 채팅으로 하던 걸 실제 저장소에 붙이려니 private repo 접근이 막혔다. 키를 새로 만들어 GitHub에 등록하는데, 등록 순간 sudo 모드(2FA)가 떠서 이 단계는 사람이 직접 승인해야 했다.
  2. 대상 사이트에 못 붙음. 테스트 대상(lomastore.com)이 이 작업 환경의 네트워크 허용목록 밖이라, Playwright를 실제로 돌려볼 수가 없었다. 다만 이건 배선 전후 똑같이 막히는 지점이라 결과 비교에는 영향이 없다.
  3. 브라우저는 있는데 뿌리가 없다. 감지/캡처를 진짜 DOM에서 검증하려고 헤드리스 크롬을 띄우려 했더니 OS 라이브러리가 없고, 설치엔 root가 필요했다. 그래서 순수 로직(지문 저장소, 액션 분류)은 유닛으로 확실히 잡고, 브라우저 의존 부분은 타입체크 + 리뷰로 남긴 뒤 "로컬/CI에서 HEAL_CAPTURE=1로 한 번 돌려 실검증"을 숙제로 명시했다.
배운 것 세 줄. ① 나중에 한 곳만 고쳐 전체에 퍼지게 하려면, 먼저 모든 접근을 함수 하나로 모아라 — 힐링은 그 다음이다. ② 몰래 살려주는 기능일수록 기록 배관을 먼저 깔아라. 통과보다 "무엇이 낡았나"가 중요하다. ③ 위험한 부수효과는 기본 off + 명시적 플래그로 가둬라. 기본 실행이 안 바뀌면 언제든 되돌릴 수 있다.

다음 글은 STEP 4 — primary가 깨졌을 때 baseline 지문으로 testid → role → label → text 후보를 훑어 실제로 힐링하고, 그 순간을 heal-report.json에 처음으로 채우는 이야기. 이어서 STEP 5에서 신뢰도 임계값과 배포 게이트(strict)로 "아무거나 잡아 통과시키는" 사고를 막을 예정이다.
