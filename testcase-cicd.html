테스트케이스 변경을 검증하는 CI 운영 구조

CSV 원본부터 브라우저 실행까지, 변경 검증을 앞당기고 결과를 분류하는 운영 구조.

작성 Taeik게시 2026-07-30편집 2026-09-24
테스트케이스의 유지보수 비용은 편집 형식보다 변경을 검증하는 과정에 좌우된다.

원본을 한 곳으로 정하고, 잘못된 참조와 생성물 불일치를 실제 브라우저 실행 전에 검사해야 한다. 정적 검사, 핵심 경로 검사, 상세 회귀 검사를 나누면 실패 원인도 더 쉽게 분류할 수 있다.

2026-07-30의 개선 제안을 바탕으로, 2026-09-24에 확인한 운영 구조를 구분해 정리했다. 아래의 “현재 적용”은 코드에서 확인한 범위이며, 장기간의 무결함 실행을 뜻하지 않는다.

이 글의 순서
  1. 수정은 빨라도 오류 발견은 늦었다
  2. 편집 원본은 하나, 변환 방향도 하나
  3. 빠른 검사와 실제 사용자 흐름 검사를 나눈다
  4. 실행 결과를 하나의 통과율로 합치지 않는다
  5. 아직 제안으로 남겨 둔 자동화

1. 수정은 빨라도 오류 발견은 늦었다

초기 운영에는 예약 실행과 결과 보고가 있었지만, 테스트케이스를 수정하는 순간의 검증이 부족했다. 존재하지 않는 요소 이름을 입력해도 다음 예약 실행까지 오류를 발견하지 못할 수 있었다. README의 테스트 목록도 별도로 관리해 원본과 문서가 달라질 여지가 있었다.

여기서 CI(Continuous Integration, 지속적 통합)는 변경할 때 자동 검사를 실행하는 과정이다. CD는 검증된 변경을 전달하거나 배포하는 과정이다. 이 글의 중심은 서비스 배포가 아니라 테스트 명세와 실행 코드의 변경 검증이다.

2. 편집 원본은 하나, 변환 방향도 하나

7월에는 들여쓰기로 구조를 표현하는 텍스트 형식인 YAML을 원본으로 유지하고 읽기용 표를 생성하는 방식을 제안했다. 이후 실제 운영에서는 표 형태의 편집을 지원하기 위해 CSV를 원본으로 채택했다. CSV는 행과 열을 텍스트로 저장하므로 스프레드시트에서 편집할 수 있고 Git에서도 변경 내용을 비교할 수 있다.

CSV 원본 편집 → YAML 생성 → 원본과 생성물 비교 → 실행 전 검사 → 브라우저 테스트
파일역할편집 원칙
test-cases.csvID, 제목, 우선순위, 상태 등 케이스 정보명세 변경의 원본
steps.csv케이스별 실행 단계와 결과 검사단계 변경의 원본
testcases/**/*.yaml실행 엔진이 읽는 생성 파일CSV에서 생성하고 직접 수정하지 않음

초기 제안과 파일 형식은 달라졌지만 기준은 같다. 같은 정보를 두 곳에서 독립적으로 수정하지 않는다. 생성한 YAML이 원본과 다르면 검사에 실패하도록 해 누락된 변환을 발견한다.

3. 빠른 검사와 실제 사용자 흐름 검사를 나눈다

검사목적현재 적용 범위
문법과 타입 검사실행 코드의 구조적 오류 검출TypeScript와 결과 요약 스크립트 등 검사
원본과 생성물 검사명세 불일치와 잘못된 참조 검출CSV/YAML 동기화, 데이터 변수, 중복 키, 사용자 정의 함수 등록 검사
단위 테스트작은 로직의 입력과 출력 검증계약 검사와 결과 집계 등, 실사이트 접속 없이 실행
팝업 계약 테스트팝업 처리 코드가 약속한 범위만 처리하는지 확인통제된 화면을 실제 브라우저로 실행하는 4개 시나리오
핵심 경로 검사(smoke)자주 확인할 주요 사용자 흐름 검증예약 및 main 반영 후 11개 실행
회귀 검사(regression)변경 후 기존 기능이 유지되는지 상세 확인수동으로 회귀 18개 또는 전체 29개 선택

계약 테스트는 입력과 구현 사이의 약속을 검사한다는 뜻이다. 브라우저가 필요 없는 파일 참조 검사도 있고, 팝업처럼 브라우저가 필요한 동작 검사도 있다. 둘을 같은 실행 비용으로 설명하지 않는다.

PR(Pull Request, 변경 검토 요청)에는 정적 검사를 연결했다. 다만 검사가 존재하는 것과 GitHub의 브랜치 보호 설정에서 병합 필수 조건으로 지정하는 것은 별개다. 이 글에서는 브랜치 보호 설정까지 완료됐다고 주장하지 않는다.

4. 실행 결과를 하나의 통과율로 합치지 않는다

첫 실행부터 통과한 테스트, 재시도 후 통과한 테스트(flaky), 끝내 실패한 테스트를 구분한다. 건너뛴 테스트(skipped)와 브라우저 시작 실패 같은 실행 오류도 별도 항목이다. 재시도 통과는 원인이 해결됐다는 증거가 아니다.

현재 예약 실행은 매일 한국 시간 오전 9시에 핵심 11개를 검사한다. 전체 회귀는 수동 실행으로 분리했다. 매일 전체 29개를 검사한다고 해석하면 안 된다. 실패 결과에는 실행 버전, 대상 범위, 테스트 ID와 실패 단계를 함께 남긴다.

이 운영에서 사용하는 기본 검사 명령은 다음과 같다. testcases:import는 CSV를 읽어 YAML을 갱신한다.

npm run testcases:import
npm run check
npm run test:overlays
npm run test:smoke
# 상세 회귀를 확인할 때 별도로 실행
npm run test:regression

npm run check가 성공해도 실제 사이트의 정상 동작이 입증되지는 않는다. 파일 검사와 브라우저 테스트는 서로 다른 질문에 답한다.

5. 아직 제안으로 남겨 둔 자동화

  • 변경 영향에 따른 테스트 선택: 수정한 TC만 실행하면 공유 셀렉터나 공통 함수의 영향을 놓칠 수 있다. 의존 관계를 확인할 수 있을 때 선택 실행을 적용한다.
  • 셀렉터 수정 제안: 화면 요소 식별 규칙이 달라지면 수정안을 만들 수 있다. 자동 대체가 완성되지 않은 현재 상태에서 수정 PR 생성까지 동작한다고 설명할 수는 없다.
  • 문서 자동 생성 확대: 목록, 재검토 대상, 실행 범위를 원본에서 생성하는 방향이다. 현재 도입된 검사와 앞으로 만들 생성기를 구분해 관리한다.

우선순위는 오류 검출을 앞당기는 검사, 결과의 추적 가능성, 편집 편의성 순으로 잡았다. 자동 수정은 마지막 단계다. 수정된 테스트가 더 쉽게 통과하는 것보다 원래 검증 의도를 유지하는지 판단할 근거가 먼저 필요하기 때문이다.
