같은 코드로 어제는 통과했던 테스트가 오늘은 절반 가까이 실패했어. 배너, 약관, 인기상품, 검색이 함께 실패했지만, 먼저 봐야 할 것은 각 기능의 셀렉터보다 공통 진입점이었어. 홈에 나타난 이벤트 팝업이 배경 조작을 막고 있었어.

2. 보이는데 찾을 수 없는 이유

브라우저에서 홈을 열자 추석 이벤트 팝업이 나타났어. 배경 영역에는 inert가 적용돼 있었어. 팝업 뒤에 HTML과 화면이 남아 있어도 조작 대상에서 제외될 수 있고, 역할 기반 로케이터는 해당 요소를 찾지 못할 수 있어.

팝업이 열린 동안 배너 버튼과 약관 링크는 0개로 탐색됐어. 닫기 버튼을 누르고 닫힘 처리가 끝나자, 실패했던 다섯 로케이터가 각각 1개씩 요소를 찾았어. 기다리는 시간만 늘려서는 사용자가 닫아야 하는 팝업이 사라지지 않아.

3. 안전한 팝업 처리

모든 닫기 버튼을 누르면 주문 확인창이나 로그인 안내까지 사라질 수 있어. 자동 처리 대상을 이벤트 팝업 링크와 오늘 더 보지 않기 버튼을 함께 포함한 dialog로 제한했어. 해당 영역 안의 닫기 버튼으로만 닫아.

각 테스트 시작 시 Playwright의 addLocatorHandler를 등록해. 조작 가능 여부를 검사하는 동작이나 자동 대기 assertion 전에 팝업이 감지되면 닫고 원래 동작을 이어가. 진입 직후 한 번만 검사하는 방식과 달리 늦게 나타나거나 다시 뜨는 팝업도 처리할 수 있어.

getAttribute처럼 속성을 읽기만 하는 동작에는 이 감지가 실행되지 않으므로, 배너와 인기상품 링크의 주소를 읽기 전에 toBeVisible 검증을 추가했어. 업무 동작 전체를 재실행하지 않아서 장바구니 담기 같은 동작을 중복 수행하지 않아.

컨테이너 대신 실제 닫기 버튼을 감지

첫 구현에서는 dialog 자체를 감지했지만 실사이트에서 동작하지 않았어. 팝업 컨테이너의 크기가 0으로 잡히는 구조였어. 그래서 실제로 보이는 닫기 버튼을 감지 대상으로 바꾸고, 이 구조도 브라우저 검증에 포함했어.

import { expect, test, type Page } from '@playwright/test';

// 이벤트 팝업만 식별해. 주문 확인, 로그인 안내 등 업무용 dialog는 건드리지 않아.
export async function installOverlayHandler(page: Page) {
  const popup = page.getByRole('dialog').filter({
    has: page.getByRole('link', { name: /^이벤트 팝업:/ }),
  }).filter({ has: page.getByRole('button', { name: '오늘 더 보지 않기', exact: true }) });
  // dialog 컨테이너가 크기 0인 사이트 구조도 있어 실제 닫기 버튼을 감지해.
  const close = popup.getByRole('button', { name: '닫기', exact: true });
  let dismissed = 0;
  await page.addLocatorHandler(close, async () => {
    await test.step(`이벤트 팝업 닫기 (${++dismissed}/3)`, async () => {
      await close.click();
      await expect(close).toBeHidden();
      // 닫힘 애니메이션 뒤 배경의 inert가 해제될 때까지 기다려.
      await expect(page.locator('header').locator('xpath=ancestor-or-self::*[@inert]')).toHaveCount(0);
    });
  }, { times: 3 });
}

닫기 버튼이 사라지고 헤더와 상위 영역의 inert가 해제될 때까지 기다려. 처리 횟수는 테스트당 최대 3회이고, 각 처리는 test.step으로 리포트에 남겨. 네 번째 팝업부터는 더 닫지 않으므로 원래 동작이 진행되지 않으면 제한 시간 초과로 실패해.

알 수 없는 팝업과 업무용 확인창은 자동으로 닫지 않아. 감지 조건이 다른 새 팝업은 별도 식별 규칙과 검증을 추가해야 해.

팝업 해결과 전체 안정화는 구분했어

HOME-005는 팝업을 닫고 상품 상세까지 이동한 뒤 장바구니 담기 버튼을 5초 안에 찾지 못하는 문제가 로컬에서 남았어. CI 통과만으로 이 문제까지 해결됐다고 결론 내리지 않았어. 가격 정렬 회귀 2개도 이번 smoke 범위에 없으므로 해결 여부를 갱신하지 않았어.

5. 이번에 남긴 기준

  • 여러 TC가 동시에 실패하면 공통 진입점과 실패 단계를 먼저 비교해.
  • 팝업은 진입 시점뿐 아니라 동작 직전에도 나타날 수 있어.
  • 자동 복구는 식별 범위와 횟수를 제한하고 처리 기록을 남겨.
  • 복구 이후 원래 기대 결과 검증은 유지해. 팝업을 닫은 것과 업무 기능이 정상인 것은 별개야.
