이벤트 팝업으로 막힌 테스트: 원인 분석과 대응

홈에서 함께 실패한 5개 테스트를 분석하고, 팝업 처리와 재검증 결과를 구분한 기록.

작성 Taeik게시 2026-09-24편집 2026-09-24
홈에서 시작하는 5개 테스트의 동시 실패를 조사하고, 식별된 이벤트 팝업을 닫는 처리를 추가했다.

수정 후 CI의 핵심 경로 검사 11개는 재시도 없이 통과했다. 다만 로컬에서 남은 상품 상세의 간헐적 실패는 별도 문제로 유지했다.

2026-09-24의 분석과 수정 버전 d30c41a 기준이다. CI 실패 당시의 trace, 즉 브라우저 동작과 화면 상태를 기록한 파일을 직접 확인한 것은 아니다. 실패 로그, 당시 브라우저 재현, 수정 후 CI 결과를 연결한 진단이며 각 근거의 범위를 구분한다.

이 글의 순서
  1. 기능은 달라도 실패한 출발점은 같았다
  2. 팝업 뒤의 화면이 조작 대상에서 제외됐다
  3. 자동 처리의 대상과 횟수를 제한했다
  4. 처리 코드와 실제 사이트를 따로 검증했다
  5. 자동 복구 후에도 원래 성공 기준은 유지한다

1. 기능은 달라도 실패한 출발점은 같았다

CI(지속적 통합)는 코드 변경 시 자동 검사를 수행하는 과정이다. 이 프로젝트는 GitHub Actions에서 변경 후 검사와 예약 검사를 실행한다. 9월 23일에는 핵심 경로 검사(smoke) 11개가 모두 통과했다. 다음 날에는 동일한 코드 버전 7fcdc45에서 6개 통과, 5개 실패가 발생했다. 실패한 5개는 재시도에서도 통과하지 못했다.

테스트 ID찾지 못한 요소
HOME-003배너의 첫 슬라이드 버튼
HOME-007화면 하단의 이용약관 링크
HOME-001헤더의 스토어 링크
HOME-005헬스케어 인기상품 카드
SEARCH-001헤더의 검색 버튼

모두 홈에서 시작했으며, 상품 상세, 장바구니, 주문서, 스토어에서 시작한 케이스는 통과했다. 각 요소의 식별 규칙이 동시에 바뀌었다고 가정하기보다 홈의 공통 상태부터 확인했다.

이전 HOME-007 실패는 클릭 후 이동하지 않는 증상이었다. 이번에는 클릭할 링크를 찾는 단계에서 멈췄다. 같은 ID라도 실패 단계가 다르면 동일 원인으로 묶지 않는다.

2. 팝업 뒤의 화면이 조작 대상에서 제외됐다

브라우저 재현에서는 홈에 이벤트 팝업이 나타났고, 배경 영역에 inert 속성이 적용돼 있었다. 이는 팝업 뒤 영역의 사용자 상호작용을 막는 상태다. 화면 구조가 남아 있어도 역할과 이름으로 요소를 찾는 로케이터는 대상을 찾지 못할 수 있다.

팝업이 열린 동안 배너 버튼과 약관 링크의 탐색 결과는 0개였다. 닫기 버튼을 누르고 닫힘 처리가 끝난 뒤에는 실패했던 5개 로케이터가 각각 1개씩 대상을 찾았다. 팝업이 같은 실패 패턴을 만들 수 있음은 재현으로 확인했다. 다만 이 사실을 CI의 당시 화면까지 직접 확인한 것으로 표현하지 않는다.

사용자가 닫아야 하는 팝업은 대기 시간을 늘리는 것만으로 해결되지 않는다. 테스트가 계속 진행하려면 어떤 팝업을 닫아도 되는지 먼저 식별해야 한다.

3. 자동 처리의 대상과 횟수를 제한했다

모든 “닫기” 버튼을 누르면 로그인 안내나 주문 확인 창까지 사라질 수 있다. 처리 대상은 이벤트 팝업 링크와 “오늘 더 보지 않기” 버튼을 함께 포함한 대화상자로 한정했다. 그 안의 닫기 버튼만 조작한다.

각 테스트 시작 시 Playwright의 addLocatorHandler를 등록한다. 클릭 등의 조작 가능성 검사나 자동 대기 assertion 전에 해당 버튼이 감지되면 팝업을 닫고 원래 검사를 이어간다. 계속 감시하는 별도 작업은 아니며, 해당 검사가 실행되는 시점에 동작한다. 동작 조건은 Playwright 공식 API 문서에 설명돼 있다.

getAttribute처럼 속성만 읽는 호출은 이 처리를 유발하지 않는다. 따라서 배너와 상품 링크의 주소를 읽기 전에 toBeVisible로 표시 상태를 검증하도록 했다. 상품 담기 등 업무 동작 전체를 다시 실행하는 복구 루프는 추가하지 않았다.

화면에 보이는 닫기 버튼을 감지 대상으로 삼았다

초기 구현은 대화상자 전체를 감지했지만 실사이트의 컨테이너 크기가 0으로 잡혀 작동하지 않았다. 실제로 표시되는 닫기 버튼을 감지하도록 바꾸고 이 구조를 재현 테스트에도 포함했다.

import { expect, test, type Page } from '@playwright/test';

export async function installOverlayHandler(page: Page) {
  const popup = page.getByRole('dialog').filter({
    has: page.getByRole('link', { name: /^이벤트 팝업:/ }),
  }).filter({ has: page.getByRole('button', { name: '오늘 더 보지 않기', exact: true }) });
  const close = popup.getByRole('button', { name: '닫기', exact: true });
  let dismissed = 0;
  await page.addLocatorHandler(close, async () => {
    await test.step(`이벤트 팝업 닫기 (${++dismissed}/3)`, async () => {
      await close.click();
      await expect(close).toBeHidden();
      await expect(page.locator('header').locator('xpath=ancestor-or-self::*[@inert]')).toHaveCount(0);
    });
  }, { times: 3 });
}

닫기 버튼이 사라진 뒤 헤더와 그 상위 영역의 inert 해제를 기다린다. 처리 횟수는 테스트당 최대 3회이며, 실행 보고서에 각 처리 단계를 남긴다. 네 번째 팝업부터는 더 닫지 않는다. 원래 동작이 계속 막혀 있으면 제한 시간 초과로 실패한다.

식별 조건이 다른 새 팝업과 업무용 확인 창은 자동 처리하지 않는다. 새 유형을 추가하려면 해당 창의 목적과 식별 조건을 먼저 확인하고 보존해야 할 창이 닫히지 않는지도 검증해야 한다.

4. 처리 코드와 실제 사이트를 따로 검증했다

계약 테스트는 준비한 화면에서 팝업 처리 코드가 약속한 동작을 하는지 확인한다. 실사이트 smoke는 실제 사용자 흐름을 확인한다. CI에는 계약 테스트 4개를 먼저 실행하고 실사이트 검사를 이어서 실행하도록 반영했다.

남은 문제: HOME-005는 팝업을 닫고 상품 상세까지 이동한 뒤 장바구니 담기 버튼을 5초 안에 찾지 못하는 현상이 로컬에 남았다. CI 통과만으로 해결됐다고 결론 내리지 않았다. 가격 정렬 회귀 2개도 이번 smoke 대상에 없으므로 해결 상태를 갱신하지 않았다. 이후 예약 실행의 장기 안정성은 이 기록의 검증 범위 밖이다.

5. 자동 복구 후에도 원래 성공 기준은 유지한다

  • 여러 테스트가 동시에 실패하면 공통 진입 화면과 멈춘 단계를 비교한다.
  • 불규칙한 팝업은 화면 진입 직후뿐 아니라 동작 직전에도 나타날 수 있다.
  • 자동 처리는 식별 대상, 최대 횟수, 처리 기록을 명시한다.
  • 방해 요소를 닫은 뒤에도 상품, 금액, 이동 결과 등 원래 기대 결과를 검사한다.

팝업 처리는 검사를 수행할 조건을 회복하는 절차다. 팝업을 닫았다는 사실 자체가 업무 기능의 정상 판정은 아니다.
